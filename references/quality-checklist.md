# 提示词质量检查清单

## 推断规则（不追问原则）

**从输入关键词推断要素 → 标注[可推断] → 不追问**

| 输入关键词 | 推断角色 | 推断任务类型 | 推断格式 |
|------------|----------|--------------|----------|
| 代码、函数、API、bug、修复 | 工程师 | 编程任务 | 代码文件 |
| 分析、统计、数据、趋势、对比 | 分析师 | 分析任务 | 表格/报告 |
| 文案、介绍、宣传、标题、写 | 文案策划 | 文案任务 | Markdown |
| 设计、界面、UI、页面、布局 | UI设计师 | 设计任务 | 设计说明 |
| 算法、模型、性能、优化、加速 | 工程师 | 优化任务 | 代码/分析 |
| 重构、架构、迁移、升级 | 架构师 | 重构任务 | 代码+说明 |
| 测试、验证、检查、审查 | 测试工程师 | 测试任务 | 测试报告 |

**推断优先级：**
1. 用户明确声明 → 最高优先级
2. 关键词推断 → 中等优先级
3. 任务类型推断格式 → 低等优先级

**示例：**
- 输入："帮我写一个登录功能" → 角色=[可推断:工程师]，任务=[可推断:创建]，格式=[缺失] → 只问格式
- 输入："分析销售数据趋势" → 角色=[可推断:分析师]，任务=[可推断:分析]，格式=[可推断:表格] → 无需追问，直接重构

## 逻辑自洽检查

### 检查项

| 检查项 | 问题 | 合格标准 |
|--------|------|----------|
| 角色能力匹配 | 角色的能力边界能否完成任务？ | 角色描述包含完成任务所需的专业领域 |
| 任务目标一致 | 任务描述是否与背景信息矛盾？ | 任务目标在背景约束内可实现 |
| 格式可行性 | 输出格式是否在角色能力范围内？ | 角色能产出该格式 |

### 不合格示例

**角色能力不匹配**：
```markdown
## 角色
你是一位UI设计师

## 任务
编写Spring Boot后端API
```
→ UI设计师不具备后端开发能力，逻辑不自洽。

**修正版**：
```markdown
## 角色
你是一位5年经验的Java后端开发工程师

## 任务
编写Spring Boot后端API
```

## 零歧义性检查

### 模糊词替换表

| 模糊词 | 替换为具体描述 |
|--------|----------------|
| "优化" | "使XX指标提升XX%"或"符合XX标准" |
| "改进" | "增加XX功能"或"修复XX问题" |
| "分析" | "从XX维度分析，输出XX结论" |
| "整理" | "按XX规则分类，输出XX格式" |
| "完善" | "补充XX内容，达到XX标准" |
| "处理" | "执行XX操作，输出XX结果" |
| "提升" | "从XX提升至XX" |

### 不合格示例

**模糊任务**：
```markdown
## 任务
优化代码性能
```
→ "性能"指什么？响应时间？内存占用？并发能力？需要量化。

**修正版**：
```markdown
## 任务
将API响应时间从500ms优化至200ms以内
```

## 可执行性检查

### 必要信息清单（按任务类型）

| 任务类型 | 必须提供的信息 |
|----------|----------------|
| 编程任务 | 技术栈、代码片段或项目结构、具体功能要求 |
| 分析任务 | 数据来源、分析维度、数据范围 |
| 文案任务 | 产品信息、目标受众、风格偏好、使用场景 |
| 设计任务 | 设计类型、尺寸限制、风格参考、元素要求 |
| 调试任务 | 错误信息、复现步骤、环境配置 |

---

## 视觉清晰检查

### 结构要求

| 元素 | 使用场景 |
|------|----------|
| `##` 标题 | 分隔各主要部分（角色、任务、背景、格式） |
| 表格 | 并列信息、对比、清单 |
| 代码块 | 代码、模板、格式示例 |
| 列表 | 步骤、要点、选项 |
| 加粗 `**` | 关键词、必填项 |

---

## 快速自检清单

```
□ 角色设定明确？（含经验/专业领域）
□ 任务描述具体？（无模糊词）
□ 背景信息完整？（无缺失必要信息）
□ 输出格式明确？（含结构/风格）
□ 角色能力匹配任务？
□ 任务目标可量化？
□ AI可立即开始工作？
□ 结构清晰？（标题/表格/代码块）
```

全部通过 → 质量合格
有未通过项 → 需修正
